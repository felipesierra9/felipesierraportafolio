¿PARA QUÉ SIRVE EL MODELAMIENTO?

Modelar es dibujar el problema antes de construirlo. Un modelo entidad-relación traduce una situación real en entidades, atributos y relaciones, de modo que todo el equipo (y el cliente) interprete la información igual y los errores de diseño se detecten cuando aún son baratos de corregir.

Propuesta y problemática Fase 1

Problema. Los datos de la Liga BetPlay no los administra una sola organización: están en medios, apps de terceros, portales de estadísticas y redes sociales. Un mismo dato (las tarjetas de un jugador, el historial entre dos equipos) cambia según la fuente, y consolidar resultados suele ser manual, con riesgo de inconsistencias.

Propuesta. Una base de datos relacional que permita a una única organización centralizar y administrar internamente equipos, jugadores, partidos, resultados y sanciones, con una aplicación web de uso interno y dos roles: USUARIO (consulta) y ADMIN (registra, modifica y elimina).

OBJETIVOS ESPECÍFICOS
  • Modelar con diagrama entidad-relación en notación Peter Chen.
  • Normalizar hasta la Tercera Forma Normal (3FN).
  • Implementar en un gestor distinto a SQL Server, sobre una VM con Linux.
  • Formular consultas con álgebra relacional.
  • Desarrollar una aplicación web sencilla conectada a la base.
  • Gestionar el proyecto en GitHub con aportes de todos los integrantes.

DECISIONES DE DISEÑO
  • Inscribir es una relación ternaria (Equipo – Torneo – Jugador): el dorsal y las fechas dependen de la combinación completa, y así se conserva el historial de quien cambia de equipo.

  • La tabla de posiciones no se modela: se calcula a partir de los resultados.

Método de 5 pasos para modelar cualquier problema reutilizable

No importa si es una liga, una biblioteca o un hospital: el procedimiento es el mismo.

  1. Lee el enunciado y subraya. Los sustantivos suelen ser entidades; los verbos, relaciones.
  2. Elige un identificador para cada entidad: ¿qué dato nunca se repite?
  3. Lista los atributos y clasifícalos: simples, compuestos, multivaluados o derivados.
  4. Define las cardinalidades preguntando en los dos sentidos: “¿cuántos A tiene un B?” y “¿cuántos B tiene un A?”.
  5. Revisa: una M:N con datos propios pide una entidad o un rombo con atributos; lo que no existe sin otra cosa es entidad débil; un subgrupo con atributos propios es una especialización.

Errores comunes al modelar evítalos
  • Guardar lo que se puede calcular: edad, totales o tablas de posiciones se derivan de otros datos.
  • Olvidar los atributos de la relación: la cantidad de una compra o la nota de una matrícula no pertenecen a ninguna de las dos entidades, sino a la relación.
  • Dejar una M:N sin resolver: en tablas siempre necesita una tabla intermedia.
  • Confundir la cosa con su copia: un libro (la obra) no es un ejemplar (la copia física que se presta).
  • Repetir texto en lugar de crear una entidad: si “Bogotá” se escribe a mano en cien filas, aparecerán “bogota” y “Bogotá D.C.”.

PARA LLEVARTE

  • Modelar sirve en cualquier sistema que guarde información: tiendas, colegios, clínicas, apps de reservas.
  • Un buen modelo se prueba haciéndole preguntas: si puedes responderlas con el diagrama, está completo.
  • Dibujar primero es más barato que corregir una base de datos que ya tiene datos.

¿PARA QUÉ SIRVE LA NORMALIZACIÓN?

Normalizar es organizar los datos en tablas para que cada hecho se guarde una sola vez. Con ello se evita la redundancia y las anomalías de inserción, actualización y eliminación, y la base se mantiene consistente aunque crezca. Aquí pasamos el MER a un modelo relacional de 22 tablas en 3FN.

Decisiones sobre el borrado y las validaciones integridad
  • ON DELETE CASCADE en las entidades débiles: si se borra un partido se borra su resultado, y si se borra una participación se borran sus goles y tarjetas.
  • En los demás casos conviene bloquear el borrado para no perder historial.
  • Los rangos y valores permitidos los valida el backend; en la base quedan llaves, UNIQUE y NOT NULL.
  • La tabla de posiciones no es una tabla: se calcula con una consulta cada vez.

Normaliza una tabla paso a paso pedidos de una tienda

Una tienda guarda todo en una sola tabla. Avanza por las etapas y mira qué problema se arregla en cada una.

Las tres anomalías, con el ejemplo de la tienda por qué importa
  • Inserción: en la tabla original no puedes registrar un cliente nuevo hasta que haga un pedido.
  • Actualización: si el precio del Mouse cambia, hay que modificarlo en todas las filas donde aparece; si se olvida una, la base se contradice.
  • Eliminación: si se borra el único pedido de Luis, también se pierde que Luis vive en Cali.

Normalizar hace que cada hecho viva en un solo lugar, y estas tres situaciones dejan de ser un riesgo.

Cuándo conviene desnormalizar trade-off

Normalizar optimiza la consistencia, pero reparte los datos en más tablas y exige más JOIN. A veces se rompe la regla a propósito:

  • Reportes y bodegas de datos: se leen mucho y casi no se modifican, así que se guardan tablas ya combinadas para que respondan rápido.
  • Datos históricos: el precio de venta se copia en cada línea del pedido para que una factura vieja no cambie si el precio sube.
  • Rendimiento medido: se desnormaliza solo cuando se comprueba que un JOIN es el cuello de botella, no por intuición.

PARA LLEVARTE

  • Normalizar es preguntarse, columna por columna, “¿de qué depende realmente este dato?”.
  • Se aplica igual a una tienda, una escuela o un hospital: siempre buscas listas en celdas, dependencias parciales y dependencias transitivas.
  • Lo normal es empezar normalizado y desnormalizar con una razón medida, no al revés.

¿PARA QUÉ SIRVEN EL ÁLGEBRA RELACIONAL Y SQL?

El álgebra relacional es la base teórica de las consultas: define operaciones (selección, proyección, uniones, joins, división…) que combinan tablas. SQL es el lenguaje que las implementa. Entender el álgebra permite razonar una consulta antes de escribirla y traducirla a SQL con criterio, en lugar de adivinar.

    • A elegir tecnología por el contexto del proyecto (herramientas, tipos de datos, entorno) y no solo por popularidad, dejando documentados los límites de una edición gratuita.
      • 
          
    • Qué es un hipervisor y por qué el reenvío de puertos permite conectarse por localhost.
      • 
          
    • Que anotar los errores sirve para repetir la instalación en otro equipo.
      • 
          
    • A descomponer un proyecto en paquetes entregables y a conectar la EDT con el cronograma y el presupuesto.

    De la idea a un sistema en marcha ciclo de vida
    
    
      
    Cualquier sistema con base de datos recorre las mismas etapas. Toca una para ver qué se hace y un ejemplo de un gimnasio.
    
      
    
      
    
    
    
  
    

  
    
    Arquitectura típica de tres capas cómo se conectan las piezas
    
    
      
    Flujo de una petición
    

      Navegador (Angular, React…)
        │   HTTP + JSON
        ▼
  API / Backend (Spring Boot, Node, Django…)
        │   JDBC o driver, consultas con parámetros
        ▼
  Base de datos (Oracle, PostgreSQL, MySQL…)
    
      
      
        
    • El frontend nunca habla directo con la base: pasa por el backend.
      • 
        
    • El backend valida reglas (rangos, permisos por rol) y arma las consultas con parámetros.
      • 
        
    • La base de datos garantiza lo estructural: llaves, UNIQUE y NOT NULL.
      • 
        
    • Las tecnologías cambian, pero las tres capas son las mismas en una tienda, un banco o una app de reservas.

    Calculadora de presupuesto de un proyecto interactivo
    
    
      
    Un presupuesto separa costos directos (horas, equipos), indirectos (internet, energía, licencias) y una reserva para imprevistos. Los porcentajes por defecto se parecen a los de mi proyecto (≈ 19 % y ≈ 12 % sobre los directos).
    
      
    
        
        
        
      
    
      
    
    
    
  
    

  
    
    Hábitos que hacen que un proyecto sea repetible buenas prácticas
    
    
      
      
        
    • Descomponer el trabajo en paquetes entregables (EDT) y verificar que la suma cubre el 100 % del alcance.
      • 
        
    • Documentar los errores y su solución: así se repite la instalación en otro equipo sin empezar de cero.
      • 
        
    • Control de versiones en equipo: commits pequeños, mensajes claros y aportes visibles de todos.
      • 
        
    • Listar los riesgos desde el inicio (conexión, tiempos, aportes desiguales) y decidir cómo mitigarlos.
      • 
        
    • Dejar un README que explique cómo levantar el proyecto desde cero.
